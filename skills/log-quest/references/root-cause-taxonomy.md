# 根因分类标准

## 概述

根因分类应反映最有证据支持的故障机制，而不是简单根据异常类名或日志关键词进行分类。允许多标签，但需区分"主要根因"和"伴随现象"。

## 根因分类

### 1. 数据错误 (data_error)

**定义**：持久化数据缺失、冲突、非法、过期或关联关系不符合业务约束。

**典型场景**：
- 数据缺失、重复、格式异常
- 关联关系不一致
- 业务约束被违反
- SQL 语法错误（引用不存在的列）
- 外键/业务键无对应记录

**常见证据**：
- SQL 异常（sqlState=42S22, errorCode=1054）
- 外键/业务键无对应记录
- 状态组合违反已登记规则
- 关键字段异常（NULL、空字符串、非法值）
- 数据库 schema 不匹配

**不应直接得出的结论**：
- ❌ 一条查询无结果就认定数据不存在
- ❌ 未考虑复制延迟、事务未提交
- ❌ 未考虑软删除、逻辑删除
- ❌ 未考虑时区差异、租户过滤

**示例**：
```
错误：Unknown column 'channel' in 'where clause'
分析：SQL 查询引用了不存在的列，属于数据模型错误
根因：data_error
置信度：high（直接证据：SQL 语法错误 + 异常堆栈）
```

### 2. 逻辑异常 (logic_error)

**定义**：程序计算、分支条件、状态转换或业务规则实现行为不符合预期。

**典型场景**：
- 条件判断错误
- 状态转换错误
- 计算结果不符合已知业务规则
- 空指针异常（有明确业务逻辑原因时）
- 数组越界、类型转换错误

**常见证据**：
- 同输入出现不合理分支
- 明确的非法状态转换
- 异常堆栈指向业务逻辑代码
- 计算结果与预期不符

**不应直接得出的结论**：
- ❌ 仅凭 NullPointerException 就认定根因是逻辑错误
- ❌ 未验证空值的来源及其违反业务约束的事实
- ❌ 未区分是数据问题还是代码问题

**示例**：
```
错误：NullPointerException at OrderService.processOrder
分析：订单状态为 PENDING，但代码尝试访问已支付订单的字段
根因：logic_error（状态转换逻辑错误）
置信度：high（直接证据：状态检查 + 异常堆栈）
```

### 3. 流程异常 (flow_error)

**定义**：调用顺序、事件消费、事务边界、幂等、重试、补偿或状态推进异常。

**典型场景**：
- 流程中断
- 状态未推进
- 事件未被消费
- 前置步骤未完成
- 重复消费
- 事务/事件顺序不符

**常见证据**：
- 缺失步骤日志
- 重复消费记录
- 上游成功而下游步骤未发生
- 事务/事件顺序不符
- 幂等键冲突

**不应直接得出的结论**：
- ❌ 日志缺失不一定代表流程未执行，也可能是日志丢失
- ❌ 未考虑日志采样、索引延迟
- ❌ 未考虑异步处理的延迟

**示例**：
```
错误：订单状态仍为 PENDING，但支付服务已扣款
分析：支付成功事件未被订单服务消费
根因：flow_error（事件消费失败）
置信度：medium（支持证据：支付成功日志 + 订单状态未更新；缺失证据：消息队列状态）
```

### 4. 网络异常 (network_error)

**定义**：连接失败、超时、DNS/TLS/连接池、远端不可用等。

**典型场景**：
- 连接失败
- 连接重置
- 调用超时
- DNS 解析失败
- TLS 握手失败
- 连接池耗尽

**常见证据**：
- 明确连接异常（ConnectException、SocketTimeoutException）
- 超时日志
- 重试耗尽
- 目标服务不可达
- DNS 解析失败

**不应直接得出的结论**：
- ❌ 业务超时不一定是网络问题，也可能是数据库慢查询或线程池饱和
- ❌ 未区分是客户端超时还是服务端超时
- ❌ 未考虑服务端处理耗时

**示例**：
```
错误：Read timed out executing GET http://payment-service/api/pay
分析：调用支付服务超时，可能是网络问题或服务端处理慢
根因：network_error（需要进一步验证）
置信度：medium（支持证据：超时异常；缺失证据：网络状态、服务端日志）
```

### 5. 资源/容量异常 (resource_error)

**定义**：CPU、内存、线程池、连接池、磁盘、队列等资源瓶颈。

**典型场景**：
- 内存不足（OutOfMemoryError）
- 线程池耗尽（RejectedExecutionException）
- 连接池耗尽
- 磁盘空间不足
- 队列满

**常见证据**：
- 饱和指标（线程池使用率 100%）
- 拒绝执行异常
- OOM 错误
- 排队延迟
- 资源使用率告警

**不应直接得出的结论**：
- ❌ 只凭耗时高就确定资源瓶颈
- ❌ 未验证资源使用率指标
- ❌ 未区分是资源不足还是性能问题

**示例**：
```
错误：RejectedExecutionException: Thread pool is EXHAUSTED
分析：HTTP 处理线程池已满，无法处理新请求
根因：resource_error（线程池耗尽）
置信度：high（直接证据：异常消息 + 线程池监控数据）
```

### 6. 配置/权限异常 (config_permission_error)

**定义**：错误配置、凭据失效、权限不足、错误路由或环境配置。

**典型场景**：
- 错误配置（配置键缺失、值错误）
- 访问权限不足（401/403）
- 凭据失效（数据库密码错误）
- 错误路由（请求发到错误的服务）
- 环境配置不匹配（开发环境配置用于生产）

**常见证据**：
- 401/403 错误
- 数据库权限错误
- 配置键缺失
- 目标环境不匹配
- 认证失败

**不应直接得出的结论**：
- ❌ 权限拒绝不代表目标数据不存在
- ❌ 未区分是配置问题还是权限问题
- ❌ 未验证配置来源

**示例**：
```
错误：Access denied for user 'app_user'@'10.0.66.110' to database 'order_db'
分析：应用用户没有访问订单数据库的权限
根因：config_permission_error（数据库权限不足）
置信度：high（直接证据：权限错误消息）
```

### 7. 未知/证据不足 (unknown)

**定义**：证据不足或互相冲突，无法可靠分类。

**典型场景**：
- 关键日志缺失
- 数据源不可用
- 多个假设均未验证
- 证据相互冲突

**常见证据**：
- 关键日志缺失
- 数据源不可用
- 查询超时
- 权限拒绝
- 多个假设均未验证

**不应直接得出的结论**：
- ❌ 不允许强行选择一个确定根因
- ❌ 不得将未知状态伪装成确定结论
- ❌ 不得因为"必须给出答案"而强行分类

**示例**：
```
错误：服务返回 500，但日志和数据库均无法访问
分析：关键数据源不可用，无法确定根因
根因：unknown
置信度：unknown（证据不足）
```

## 分类优先级

当多个分类都可能时，按以下优先级选择：

1. **有直接证据的分类优先**
   - 如果某个分类有直接证据（如异常堆栈明确指向该分类），优先选择

2. **最早异常的分类优先**
   - 如果时间线中有多个异常，优先选择最早异常的根因分类

3. **主要根因优先于伴随现象**
   - 区分"主要根因"和"伴随现象"
   - 后续服务出现的异常不一定是根因，可能只是上游失败的结果

4. **如果无法确认，使用 unknown**
   - 列出最有可能的假设及缺失证据
   - 不得强行选择一个确定根因

---

## 多标签分类

同一个事故可以存在：
- **一个主要根因**：导致故障的根本原因
- **多个促成因素**：加剧故障或导致连锁反应的因素

示例：
```
主要根因：data_error（SQL 查询引用不存在的列）
促成因素：
  - config_permission_error（数据库 migration 未执行）
  - flow_error（缺少 schema 验证步骤）
```

---

## 分类规则

1. **不得仅凭异常关键词映射根因**
   - 同一异常（如 NPE、timeout）可能有多种上游原因
   - 必须结合上下文和业务逻辑判断

2. **必须区分直接原因和根本原因**
   - 直接原因：触发异常的最近事件
   - 根本原因：导致直接原因的底层问题

3. **必须考虑替代解释**
   - 列出所有可能的根因分类
   - 评估每个分类的证据支持程度
   - 选择证据最充分的分类

4. **必须记录分类依据**
   - 说明为什么选择该分类
   - 列出支持证据和反证
   - 说明置信度评估依据
